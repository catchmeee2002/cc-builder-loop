# 文档维护原则

> 适用所有项目的 .md 文档维护。builder 写 doc 前（step 3.5）强制 Read 本文件；reviewer Phase D 按本文件审计。
> 凡涉及"该写哪、该删哪、该不该写、该不该记进 memory"的判断，本文件即宪法。

---

## 0. 入口闸门（按顺序过）

### 0a. 第零道闸：消除性 — 这事该修掉，还是该记下来？

**本仓能修掉的事，任何容器都不收。** 落笔（或建议 `/memory`）前先过这一问：

> **这条事实，在正确修复之后是否依然成立？**

- **否** —— 改代码 / 测试夹具 / 配置 / CI / `.gitignore` 就能让它不再成立 → 它**不是知识，是缺陷**。归宿：当场修，或 `/file-github-issue` 立项（gh / glab 均可）。**禁止写入 memory，禁止写入任何 .md。**
- **是** —— 外部契约、平台行为、上游默认实现、组件真实边界等本仓改不动的事实 → 进入 §0b。

判据本身即答案：修完就不成立的东西写进记忆，等于把一条**马上会变假的断言**钉成长期前提；而在修好之前它也不是记忆，是 TODO。代价大（调试久、藏得深）≠ 知识稳定——**痛感不是判据，不可消除性才是**。

典型误判（这些全部走修复 / issue，不走 memory）：测试夹具与真实驱动行为不一致、跑测试污染工作区、缺 `.gitignore` 条目、脚本硬编码相对路径、CI 门禁被自家产物咬。

### 0b. 第一道闸：先判断要不要动文档

多数改动**不触及文档面**——正确动作是不动。落笔前先过这一关：

> 本次代码改动是否触及了「文档面」——对外行为 / 契约 / 导航结构 / 新增对外文件 / 架构决策？

- **否** → 直接 no-op 返回，输出一句「本次改动不触及文档面」，**不要找补式更新**。
- **是** → 进入 §1 容器矩阵分流。

找补式更新（为改而改、把实现细节灌进 .md、给稳定文档加无谓修饰）比漏更新危害更大——前者持续污染，后者下次补即可。

## 1. 容器矩阵 — 不同内容各回各家

文档质量崩坏的根因是「一个 CLAUDE.md 当六种容器用」。先按内容类型选对容器：

> **语境映射**：表中 `CLAUDE.md` 指「当前 Agent 的主文档」——Claude Code 侧是 `CLAUDE.md`，Codex 侧是 `AGENTS.md`，按执行 Agent 换算，其余判据不变。

| 内容类型 | 应该去 | 禁止去 |
|---|---|---|
| **模块导航 + 何时读** | CLAUDE.md（唯一归宿） | — |
| **架构决策**（系统怎么设计 / 为什么这么选） | CLAUDE.md 或 `docs/ARCHITECTURE.md` | — |
| **外部契约约束**（QNX 限制、字段被外部消费、协议要求等接手者必须知道的事） | CLAUDE.md「核心约束」段 | — |
| **AI 协作隐式约束**（修 X 前先读 Y、测试要 mock Z、Agent 工具坑、bash 陷阱、subagent 调用注意）<br>**限本仓改不动的外部行为**；"夹具写得不对"这类本仓可修的，走末行 | 当前 Agent 的项目记忆（路径见下） | ❌ CLAUDE.md |
| **改动史**（issue/任务/实验编号、哪个版本改了啥） | git log + `CHANGELOG.md` | ❌ CLAUDE.md |
| **待办 / 路线图**（要做的事、进行中的任务、计划项） | issue tracker（gh/glab issue + milestone/project board） | ❌ CLAUDE.md / ❌ `docs/plan.md` / ❌ README 的 TODO 段 |
| **当前快照**（模型选型、实验数据、性能数字、测试通过率、模型推荐） | 配置文件 / 数据库 / 自动生成报告（详见 §3） | ❌ CLAUDE.md / ❌ 新建 `docs/state-*.md` |
| **Debug 记录**（coredump、call stack、失败测试名、hex 地址） | `docs/known-issues.md` 或 `docs/bug-*.md` | ❌ CLAUDE.md |
| **API 签名 / 字段定义 / JSON schema** | 代码 docstring / `models.py` / schema 文件 | ❌ 任何 .md |
| **本仓可修的缺陷 / 脏状态**（夹具与真实行为不符、测试污染工作区、缺 .gitignore、硬编码路径、CI 被自家产物咬） | 代码修复 + `/file-github-issue` 立项（gh / glab） | ❌ 任何 .md / ❌ memory |

**判别简记**：先过 §0a 消除性闸（能修掉的 → 修 / issue，到此为止）；剩下的，接手者也要知道的 → CLAUDE.md；只有 AI 协作要知道的 → memory；其余各回各家。

> ⚠️ memory 是**兜底容器，不是默认容器**。"纯人工新团队不需要知道" 只能排除 CLAUDE.md，**不能反推出 memory**——先确认它没被 §0a 拦下。这条兜底缺失是 memory 被塞满可修缺陷的主因。

### Memory 路径分流

- Claude Code / CC 写入 `~/.claude/projects/<project-hash>/memory/`。
- Codex 写入 `~/.codex/memories/`：`MEMORY.md` 作总索引，项目细节放 `projects/<project-key>/`，`memory_summary.md` 只放简短路由。
- 必须按当前执行 Agent 选择路径，禁止跨 Agent 写入另一方的 memory 目录。

**「踩坑 / 约束」类专门一问**（最容易塞错的）：*这个 git 仓交给一支纯人工新团队，他们也要知道吗？* 是 → CLAUDE.md「核心约束」（外部契约性质：QNX 必须 `-lsocket`、某 RPC 字段被外部消费、协议要 3 秒响应）；否 → 当前 Agent 对应的 memory（AI 协作隐式约束：Agent hook 行为、bash `set -e` 陷阱、subagent gotcha、先读哪个文件再改、测试要 mock 哪个）。别把 AI 协作经验灌进 CLAUDE.md——既污染团队文档（接手的人看不懂），又让 memory 失去本职（跨会话私人 cache）。

## 2. CLAUDE.md 体量

- **软上限 200 行**。超了说明该思考下沉
- 父级 CLAUDE.md 短为美，详细内容下放到子模块 CLAUDE.md 或 `docs/`
- 一个有 ≥10 个代码文件或 ≥1000 行的目录，应该有自己的 CLAUDE.md（或等价的 `docs/<module>.md`），避免父级被迫膨胀
- 「导航表」是 CLAUDE.md 的核心信号——其他段落不能淹没它

## 3. 快照默认沉结构化通道（写进 .md 是反模式）

> 本节是「快照」处理的**唯一权威定义**。§1 表（当前快照行）、§4（保质期）、§5（checklist）凡涉及快照，判断一律回到本节，不在别处重复展开规则。

「当前 / 最近 / 正在 / exp-NNN 验证 / 推荐配置」类内容写进 .md 会跟实际状态漂移，下游想做统计也没法可靠 grep。正向归宿：

| 快照内容 | 应该去 |
|---|---|
| 模型选型 / 运行参数 / 阈值 | 配置文件（如 `novel.yml` / `config.py` / `.env`） |
| 实验数据 / 性能数字 / 测试通过率 | DB / `*.jsonl` / 自动生成的 report.md |
| 历史改动 | git log + CHANGELOG（**过去时态**写，不维护「当前」） |
| 进行中的事 / 待办 | issue tracker（gh/glab issue + milestone/board）；**无 tracker 的离线仓**才退回 `docs/plan.md`，且必须带 §4 保质期 |

### 待办的单一真相源：tracker

待办的**唯一真相源是 issue tracker**。.md 里只能留**一行指针**（issue 链接 / label 查询命令），**禁止镜像 issue 列表、状态、进度百分比、看板快照**。

双写必漂移——这是 §8「覆写不 append」在跨系统上的推论：tracker 持有当前态，.md 里的副本**一落笔就开始变成「曾经为真」**，而且没有任何机制会去更新它。

tracker 自带 `open/closed` + owner + 时间戳 + 可查询，**它就是 §4 保质期的原生实现**。离线仓退回 `docs/plan.md` 时之所以要手写保质期，正是因为丢了这套机制——那是降级方案，不是常态。

极少数实在没法结构化的（如部署文档里「当前推荐配置」），单一位置 + §4 保质期。

## 4. 保质期规则

任何快照 / 调试记录 / 临时决策出现在 .md 里，**节首必须标**：

```
[保质期: <事件 or YYYY-MM-DD>, owner: <name>, 正向归宿: <配置/DB/CHANGELOG 路径>]
```

例：

```
[保质期: exp-024 完成, owner: hongyu, 正向归宿: novel.yml model_config 段]
[保质期: 2026-08-01 复审, owner: hongyu, 正向归宿: docs/known-issues.md]
```

**豁免**：「架构决策」「外部契约约束」两类——本身就是稳定知识，加保质期反而误导。

无保质期标注的快照内容 = 谁看到谁有权删。

## 5. 落笔前 checklist

下笔前依次过：

- [ ] §0a 第零道闸：这条事实在正确修复后还成立吗？否 → 是缺陷不是知识，走修复 / `/file-github-issue`（gh / glab），**不写任何 .md、不写 memory**
- [ ] **这条是不是待办**（要做的事 / 进行中 / 计划项）？是 → 开 issue（gh/glab），**不写 .md**；.md 里最多留一行指针（见 §3「待办的单一真相源」）
- [ ] §0b 第一道闸：本次是否真的触及文档面？否 → no-op 返回，不找补
- [ ] §1 容器：这条改动属于哪类？不在表内 → 思考是不是不该写；踩坑 / 约束类按 §1 末那一问判 CLAUDE.md 还是 memory
- [ ] **三问自检**（三个全 ✅ 才动手，任一 ❌ → 换容器或换写法）：① 3 个月后还成立吗？② 从 git log / 配置 / DB / 自动报告能复原吗（能 → 不写）？③ 含会漂移的标识符吗（issue/实验编号、版本号、字段名/路径、hex/堆栈、性能数字、模型名、命令输出 → 默认进 CHANGELOG / 子文档，CLAUDE.md 只留一行指针）？
- [ ] CLAUDE.md：改完总行数 ≤ §2 软上限（200 行）
- [ ] 快照类内容：先尝试 §3 沉结构化通道；沉不下去才写 .md，必须加 §4 保质期
- [ ] 写完反向核对：把这段删掉，从 git log / 配置 / 自动报告能恢复信息吗？能 → 删
- [ ] 章节归位：内容放进 §7a 对应章节了吗？理论富项目另查 §7b 下降链
- [ ] 更新进展 / 状态：是否按 §8 覆写当前态、而非 append 历史？
- [ ] **写法：写触发器不写事故**——写进 CLAUDE.md 的每条内容必须是未来可复用的工程规则（"修改 X 时，先检查 Y，再跑 Z"），不是历史叙事（"上次改 X 时没找到 Y"）。事故是过去时一次性的，触发器是条件→动作可反复命中的。

## 6. 元规则

本文件未覆盖的判断（如某条改动到底算"架构决策"还是"实现细节"），用 LLM 判断力解决，不要逻辑硬编码。

错了改本文件，不改消费者逻辑——policy 是输入条件，builder/reviewer 是执行者，**改输入条件 > 改输出约束**。

---

## 7. CLAUDE.md 章节结构

### 7a. 常规项目的默认章节（扁平结构）

多数项目（集成 / 驱动 / glue / 业务模块）用扁平结构，按以下六段组织。不是每段必写——没内容的段不要凑：

| 章节 | 放什么 | 一句话标准 |
|---|---|---|
| **Project Map** | 核心目录职责、模块边界、禁止手改目录、生成代码位置 | 让 Claude 不迷路 |
| **Commands** | 经过验证的构建 / 测试 / 格式化 / 回灌命令 | 能直接复制执行 |
| **Workflows** | 什么情况先出 plan、什么情况必须扩大验证、哪些动作需人工确认 | 减少返工 |
| **Common Pitfalls** | 来自 git fix 历史的高频错误模式（构建 / 配置 / 逻辑 / 性能） | 减少重复踩坑 |
| **Collaboration** | commit 规范、CR/Issue ID、pre-commit 覆盖、发布节奏 | 贴合团队协作 |
| **References & Skills** | 指向详细 docs / reference / skill 入口；已有 skill 覆盖的只写入口不复制步骤 | 保持短而准 |

往 CLAUDE.md 加内容时，先按此表选目标章节。章节不存在且确有必要时才新建，不主动铺满六段。

### 7b. 理论富项目的主文档结构（下降链）

> **Scope 闸**：本节只对**理论富项目**成立（系统设计能从少数第一性原则派生，如叙事引擎）。contingent-facts 为主的项目（集成 / 驱动 / glue）**不适用**——强行写成下降链会**制造假理论当根**，反而误导。**深度 ⟂ 理论可派生性**：项目再复杂，若它的复杂是堆事实不是推原则，就按默认扁平结构写，不强凑。

主文档的**结构本身是 payload**——读者（含维护文档的 LLM）被结构塑形认知：扁平断言传"服从 / 查表"，下降链传"跟着再下一层"。故理论富项目的主文档（CLAUDE.md）应写成三层下降链：

1. **理论基底**（第一性原则，auto-load）——系统为什么这样设计
2. **严密派生工程**（逻辑可追溯）——从基底推出的数据结构 / 流程 / 决策
3. **不可派生的经验护城河层**（显式标注"不可从原则推导、来自经验积累"）——这层是真正的护城河（可派生的是入场券，不可派生的过程纪律才独有）；纯"基底 → 派生"会漏掉它，**它不是优雅结构上的疣，是价值本体**。

**容器判据**（内容放主文档还是下沉）：不看"详不详细"，看**要不要在动手那刻 auto-fire**——原地 auto-load 的纪律留主文档，查阅型细节 on-demand 下沉。（注：`auto-fire` 概念本身域限于"读者是有 auto-load 机制的 agent"，对纯人类读者失指称。）

## 8. 更新轴：覆写不 append（当前态 = 历史的 fold）

文档"拉屎"（长期项目里一节攒一堆过期的历史决策 / 实验 / 实现）的根因 = **append-only 历史和当前态混在一节**。修法：

- **进展 / 状态 = 覆写**，不追加。当前态是历史的 **fold**（把变更累加算出此刻值）——写当前态、**覆盖**旧的。
- **过期历史**：删（git 可复原），或归 CHANGELOG（过去时态）。不堆进"进展"节。
- **承重决策理由**：策展进决策节 / CHANGELOG，不和进展日志混。

> 为什么默认会 append：append 是安全默认（不丢信息）。但对"当前态"它用"曾经为真"污染"此刻为真"——得**显式压下去**。与 §3 快照沉结构化通道同源：当前态不进 append 流。

---

## 9. builder-loop runtime 契约

> 本节只对 builder-loop 的执行者成立，不构成对文档内容的判断规则。

- **Builder 负责写文档；Reviewer 独立判断**是否该写、写到哪里、是否与代码和计划一致。
- **本文件不可读取时停止 Phase D**，不自行发明替代规则。
