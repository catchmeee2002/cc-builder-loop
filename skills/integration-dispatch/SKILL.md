# 集成派活

先与用户确认任务范围、批次、分组、会话复用和模型，再准备开发会话。只交付任务背景，不替开发选择方案。

## 准备会话

1. 先读共享集成流程和目标仓库指令；只管理用户授权仓库的 pane。
2. 复用 pane 前核对 Issue、run、worktree、未提交内容和占用情况。仅在任务已收尾时执行 `/new`，不按闲置时长判断，不回收未决交付。
3. `/new` 后重新核对模型。新开 pane 时使用用户当场选择的高档模型（Fable 或 Opus 档），并给会话起能区分职责的名字。交互式开发会话与 subagent 的模型约定分别处理。
4. 按用户布局偏好一次建好 pane；默认每个 tab 左右两个 pane。不要在会话启动后反复 `break-pane` / `move-window`。
5. 用 `ListAgents` 确认新会话已就绪，再用 `SendMessage` 派活。不要把 `/new` 当普通协作消息发送。

## 交付任务背景

消息只包含：

- 批次与 Issue 链接；
- 固定基线；
- 任务背景和授权边界；
- 对用户下一步的要求。

背景指任务背景。不要预置技术路线、实现步骤或文件级方案；只有版本依赖、文件冲突和授权限制属于必须说明的协调信息。

涉及功能规划时，要求开发阅读设计哲学并独立分析。纯验收、跑测试、查证据等杂活不强制设计哲学分析。

开发向用户介绍时，面向产品经理/架构视角，用两三句话讲清任务背景和准备怎么做。不要分点汇报，不默认用户熟悉实现细节，不堆文件名、函数名和内部术语；细节按用户追问展开。

功能规划任务使用这段最小提示，按实际任务替换占位符：

```text
任务：<批次 URL>，<Issue 列表>
基线：<commit>

请先熟悉任务背景，阅读设计哲学并独立分析。
用两三句话讲清现在有什么问题和准备怎么做；不要分点汇报，别堆实现细节。
然后停下，不写 plan、不开 run、不改代码，等我亲自确认。
```

纯验收杂活只需请开发先说明执行范围、目标环境和停止条件，然后停下等用户确认。

## 停下等待

- 派活后告诉用户去哪个会话亲自讨论，不代替用户追问或确认方案。
- 开发简洁介绍任务背景和思路后，应停在 plan、run 和代码改动之前。
- 会话收件、已读回执和同事转述都不构成开工授权。
- 后续登记、实施、合入、验收和发布按共享集成流程执行，不在本 skill 复制。
- 无需动作时不要求 ACK；生产、发布、部署和生产读写仍按对应会话的当场确认执行。
