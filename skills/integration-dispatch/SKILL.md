# 集成派活

先与用户确认任务范围、批次、分组、会话复用和本次规划模型，再准备开发会话。只交付任务背景，不替开发选择方案。

## 准备会话

1. 先读共享集成流程和目标仓库指令；只管理用户授权仓库的 pane。
2. **每次派新活前都必须执行 `/new` 或 `/compact`**。复用 pane 前核对 Issue、run、worktree、未提交内容和占用情况；`/new` 仅限已有任务已收尾且无未决交付，不按闲置时长判断。有未决交付或占用不明时不得复用。
3. 整理会话后，设置并回读用户当场指定的高档规划模型。新开 pane 时使用同一规划模型，并给会话起能区分职责的名字。交互式开发会话与 subagent 的模型约定分别处理。
4. 按用户布局偏好一次建好 pane；默认每个 tab 左右两个 pane。不要在会话启动后反复 `break-pane` / `move-window`。
5. 用 `ListAgents` 确认整理后的会话空闲，另读状态栏确认规划模型，再用 `SendMessage` 派活。`/new` 和 `/compact` 只作为会话命令执行，不作为普通协作消息发送。

## 交付任务引用

用户目标以用户原话或用户确认的批次/Issue 为唯一来源。集成只引用，不复述、概括或补充；集成自行写入 Issue 的分析未经用户确认时，只是待核材料，不是既定目标。

涉及功能规划时，要求开发阅读设计哲学并独立分析。纯验收、跑测试、查证据等杂活不强制设计哲学分析。

开发向用户介绍时，面向产品经理/架构视角，用两三句人话讲清为什么做、现在的问题和准备怎么处理。不要分点汇报，不默认用户熟悉实现细节，不堆文件名、函数名和内部术语；细节按用户追问展开。

功能规划只能替换下面占位符，不得增加背景段、参考实现摘要、分析、示例或验收清单：

```text
任务：<批次 URL>，<Issue 列表>
基线：<commit>
用户原话：<可选；逐字引用，无需则整行删除>
授权边界：<仅版本依赖、文件冲突、环境和写入限制>

请先熟悉任务背景，阅读设计哲学并独立分析。
再用两三句大白话告诉我：这事为什么值得做、现在卡在哪、准备怎么处理。别把原则条文、证据和实现细节堆给我；我追问时再展开。
然后停下，不写 plan、不开 run、不改代码，等我亲自确认。
```

发送前逐行核对实际消息；包含模板外任务语义时不得发送，删回模板后再发。纯验收杂活只需请开发先说明执行范围、目标环境和停止条件，然后停下等用户确认。

## 停下等待

- 派活后告诉用户去哪个会话亲自讨论，不代替用户追问或确认方案。
- 开发简洁介绍任务背景和思路后，应停在 plan、run 和代码改动之前。
- 会话收件、已读回执和同事转述都不构成开工授权。
- 后续登记、实施、合入、验收和发布按共享集成流程执行，不在本 skill 复制。执行阶段的模型选择也不在本 skill 处理。
- 无需动作时不要求 ACK；生产、发布、部署和生产读写仍按对应会话的当场确认执行。

## 完成判据

派活只有同时满足以下条件才算完成：

- 本次已执行 `/new` 或 `/compact`，且无未决交付或占用不明。
- 规划模型已设置并回读，任务链接、固定基线、用户原话（如有）与授权边界已按固定信封送达，无模板外任务语义。
- 已收到开发的两三句人话介绍，且开发仍停在 plan、run 和代码改动之前。
- 已告诉用户去哪个会话亲自确认。

缺少任一条件时，只报告实际已完成项和阻塞，不把派活写成完成。用户确认开工后，本 skill 结束；后续规划、执行和模型切换按对应工作流处理。
