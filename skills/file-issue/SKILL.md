# 提交 Issue（GitHub / GitLab）

把仍然新鲜的问题现场保存进责任仓库。不要替后续诊断提前决定修法。

## 判断授权

- 用户已经说“提 Issue”“记录 bug”或同义指令时，直接执行；这条指令已经授权创建或补充 Issue，
  不要再次询问是否创建、标题是否合适或正文是否确认。
- 当前任务明确要求自动记录运行中发现的缺陷时，同样直接执行。
- 只是在其他任务中顺手发现可疑问题、但没有创建授权时，只向用户报告，不写入任何平台。
- 仓库归属不明确、证据可能含凭据或个人数据、问题实际要求改变产品目标或设计原则时，停止创建并
  使用 `request_user_input` 处理这个异常；不要把普通字段缺失升级成人工审批。

## 判定平台（GitHub 还是 GitLab）

1. 先确定目标责任仓库，再看它的 remote 归属，不要凭仓库名或路径猜测：
   - remote 是 `github.com`（或用户显式指定的 GitHub 企业域）→ 用 `gh`。
   - remote 是内网/自建 GitLab（如 `gitlab.*`，或用户显式指定的 GitLab 实例）→ 用 `glab`，必要时加 `-R <namespace>/<repo>` 或 `--repo` 显式指定项目路径。
2. 两个 CLI 在同一次任务里可能都要用（例如一个是 GitHub 项目、另一个缺陷实际该记在内网 GitLab 平台），按各自归属分别处理，不要混填。
3. 目标平台的连通性异常（DNS 失败、代理拦截、认证失败等）属于环境问题，应先定位并向用户报告，不要绕过校验或静默切换平台。

## 保留现场

1. 先读取适用的项目指令和设计原则，确定 Issue 应归属的唯一责任仓库以及被违反的预期契约。
2. 在现场消失前收集触发场景、实际执行过程、可复现步骤、观察到的现象、预期行为和已确认事实。
   无法稳定复现时如实记录尝试和边界，不要补造复现步骤。
3. 记录能精确定位现场的证据，例如命令及退出码、日志或 run 引用、相关文件、commit、当前
   `HEAD`、branch 和 dirty 状态。只摘取有效片段，不把无关长日志倾倒进 Issue。
4. 清洗 token、Authorization header、带凭据的 remote URL、个人数据和其他秘密。安全漏洞或无法
   确认可公开的证据不得发到普通 Issue。
5. 将根因状态明确写成以下一种：
   - `unknown`：尚未诊断；
   - `candidate`：存在能解释现场的假设，但仍有竞争解释或缺少证据；
   - `confirmed`：已有直接证据排除合理替代解释。
6. 不把模型推断写进“已确认事实”。默认不写修法、建议或实施方案；Issue 负责保留问题，不负责
   锚定后续诊断。

## 查重并写入

1. 按上面“判定平台”确认目标 repository 及使用的 CLI；不要把业务项目、builder-loop 和外部平台
   缺陷混在同一个 Issue。
2. 查重：
   - GitHub 用 `gh issue list --state all --search ...`；
   - GitLab 用 `glab issue list --all --search ...`（或 `glab api "projects/<id>/issues?search=..."`）。
   不能只按标题查重，要核对触发条件、现象和责任边界是否同一个原子问题。
3. 找到同一原子问题时，追加而不是新建：
   - GitHub 用 `gh issue comment`；
   - GitLab 用 `glab issue note`（或等效命令）。
   把新的现场和版本证据追加到原 Issue，并返回该链接。现象相似但根因或责任仓库不同的，分别创建并互相链接。
4. 没有重复项时，由当前 Agent 直接运行对应平台的创建命令：
   - GitHub：`gh issue create`；
   - GitLab：`glab issue create`（跨仓库场景显式带 `-R <namespace>/<repo>`）。
   标题描述可观察症状，不把未经确认的根因或修法写进标题。若该 CLI 需绕过代理等本机特殊设置（如内网
   GitLab 域名应直连、不走通用代理），按已知项目约定处理，不要为了连通而静默切换平台或跳过校验。
5. 正文按现场实际信息组织，至少让后续 Agent 能分清：
   - 归属与版本；
   - 触发场景和现场过程；
   - 观察到的现象；
   - 预期契约；
   - 已确认事实和证据引用；
   - 根因状态及其依据；
   - 复现稳定性和仍缺少的证据。
6. 创建或补充完成后，核对返回的 repository、Issue 编号和 URL，只向用户简短报告结果；除非用户
   另有要求，不继续分析、分流或修复。
