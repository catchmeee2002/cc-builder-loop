# cc-builder-loop 设计哲学

> 本项目是 LLM 驱动的发散系统——Claude Code 的行为不确定，中间件层（hook / prompt / state / subagent）互相耦合，打补丁会滚雪球。以下原则是所有设计决策的判据。

## 一、机器判据，不是 LLM 意见

状态转移只靠客观可验证的信号（测试通过、文件存在、exit code），不靠 LLM 的主观判断。LLM 说"我改好了"不算通过——命令跑过了才算。

## 二、每份数据有且只有一个家

同一个事实不存两个地方。需要某个信息就去它的唯一源头读，不在消费侧缓存副本。冗余必漂移，漂移必出事。

## 三、显式授权，默认拒绝

不认识的东西不碰。不是我的 loop 不操作，不是我的 worktree 不写入，不是我请求的 dirty 不带进来。宁可多一步显式声明，不省一步引入隐式耦合。

## 四、改输入条件，不改输出约束

行为不对时，改数据结构和架构让正确行为自然发生，不在末端加特判堆约束。约束堆得越多系统越脆，因为每个约束都是一个"LLM 可能不遵守"的点。

## 五、同一个问题出现三次就是架构缺陷

单点修复只治标。同一模式的 bug 反复出现说明缺一层抽象或一道边界。找到共同根因，一次修掉。

## 六、契约先于实现

每个可执行单元（hook / 脚本 / subagent）先定义它的输入、输出和副作用契约，再写实现。测试验证契约是否被遵守，不验证实现细节。实现可以随时换，契约不能随便变。
