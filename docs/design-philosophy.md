# cc-builder-loop 设计哲学

> 本项目是 LLM 驱动的发散系统——Claude Code 的行为不确定，中间件层（hook / prompt / state / subagent）互相耦合，打补丁会滚雪球。以下原则是所有设计决策的判据。
> 原则零是项目的正向定位（在生态里占什么位），原则一至六是防御发散的约束，原则七约束本仓库自身。

## 零、判据分层编排器（项目定位）

本项目在 AI 协作生态里占的位是：**为自动化系统提供 ground truth 锚点**。

LLM 判官（reviewer / 对抗验证 / 官方 workflow 的 verify 阶段）会越来越强，但它判的本质是「LLM 判 LLM」——存在同源偏差，且可被 reward hacking 攻击（删测试、弱化断言，且自己真诚地认为做对了）。机器判据（测试退出码）是唯一不被同源偏差污染、不可被话术说服的外部锚点。

**LLM 判官越强，越需要这个锚点防止它飘。** 本项目不跟 LLM 判据竞争，而是做它的地基——把能写出客观判据的部分钉死成 ground truth，让上层的 LLM 判断有一个说服不了的参照。

## 一、判据分层：机器判据兜底，LLM 判据补语义

判据是一条可验证性谱系，不是二选一。两类判据覆盖**不同类的错误**，像类型系统 vs 测试，谁也不取代谁。

- **机器判据**（测试通过 / 文件存在 / exit code）：可证伪、零成本重放、不可被说服。做 **ground truth 地基**——必要条件 / 硬门禁 / 防作弊兜底。LLM 说"我改好了"不算通过，命令跑过了才算。
- **LLM 判据**（reviewer / judge / 对抗验证）：覆盖机器测不到的语义——可读性、架构是否合理、需求是否真的被满足。做**上层**——充分条件 / 质量维度。但 LLM 判 LLM 有同源偏差，必须用对抗验证 / 多 lens 降偏，**不单票放行**。

**分层规则**：能写出机器判据的层，机器判据优先且兜底；写不出客观判据的语义层，才上 LLM 判据，且必须降同源偏差。

## 二、每份数据有且只有一个家

同一个事实不存两个地方。需要某个信息就去它的唯一源头读，不在消费侧缓存副本。冗余必漂移，漂移必出事。

## 三、显式授权，默认拒绝

不认识的东西不碰。不是我的 loop 不操作，不是我的 worktree 不写入，不是我请求的 dirty 不带进来。宁可多一步显式声明，不省一步引入隐式耦合。

## 四、改输入条件，不改输出约束

行为不对时，改数据结构和架构让正确行为自然发生，不在末端加特判堆约束。约束堆得越多系统越脆，因为每个约束都是一个"LLM 可能不遵守"的点。

## 五、同一个问题出现三次就是架构缺陷

单点修复只治标。同一模式的 bug 反复出现说明缺一层抽象或一道边界。找到共同根因，一次修掉。

## 六、契约先于实现

每个可执行单元（hook / 脚本 / subagent）先定义它的输入、输出和副作用契约，再写实现。测试验证契约是否被遵守，不验证实现细节。实现可以随时换，契约不能随便变。

## 七、本项目自身也受这些原则约束（dogfooding）

以上原则不只约束被构建的系统，也约束本仓库自身的文档与代码。

本文档曾出现六条原则同时存在于三处（`design-philosophy.md` / `CLAUDE.md` / `README.md`）——**这是原则二的违反点**：哲学文档自己没遵守哲学。发现即收敛：哲学正文只有这一个家，`CLAUDE.md` / `README.md` 只留导航指针。

落地约束：
- **文档放置按使用频率分层**——每轮都要遵守的操作规则进根 `CLAUDE.md`（CC 每轮自动加载），做架构决策时才查的判据进独立文档（按需读）。哲学属后者。
- 任何"为了方便再抄一份"的冲动，都是原则二的违反点，用指针代替复制。
