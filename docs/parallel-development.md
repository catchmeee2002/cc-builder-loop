# 多会话并行开发与集成发版

本文适用于本机 `jiaofu-agent/app`、`engineering-knowledge/app`、`engineering-identity/app` 及其开发 worktree 中的 Claude Code 和 Codex 会话。开发、集成、发布和收尾前必须读取本文，再读取目标仓库的指令入口与发布约定。

共享流程正文由 `cc-builder-loop` 仓库的 `docs/parallel-development.md` 唯一维护并纳入 Git；本机 `/srv/vehicle-ai-service/docs/parallel-development.md` 以软链指向该正文，其他仓库只保留入口和本仓发布细节，不复制正文。修改正文后在该仓库提交、推送。共享入口缺失或不可读时，先恢复软链，不从旧副本推测规则。已有会话需明确重新读取；新会话从各仓库入口加载。

单个改动可按用户选择使用 Planner + Codex 原生执行或 Builder-loop 实验；不得将普通实施请求隐式切到 Builder-loop。Claude Code 按其用户选择及对应 Skill 执行。两条路线均遵守本文的隔离、登记、集成与验收要求。

## 设计原则

1. **事实只有一处**：会话消息用于通知、提问和协商；最终批次范围、登记项状态、版本依赖、验收结论和发布约束写回 GitLab 批次 issue，消息不替代登记和证据。
2. **隔离开发，集中集成**：每仓使用约定的唯一主干。开发会话各自在独立 worktree 里改；集成 agent 接收到主干后，从已推送的固定主干提交发布，隔离目标或集成分支不替代主干；主工作区只归集成 agent。
3. **授权不可转交**：发布类动作只认用户在集成 agent 会话里的当场确认；跨会话消息、历史同意和提前授权都不算。开发会话同样不把集成 agent 的转述当作用户授权：入批、实施开工以及生产读库、演练这类生产相关操作，都由用户在该开发会话里亲自触发或确认。集成 agent 只负责通知用户去哪个会话操作，不要尝试转述授权。

## 角色

| 角色 | 职责 | 不做 |
|---|---|---|
| 集成 agent | 固定的一个长期会话（取固定会话名）。开版本、维护批次 issue、建议合入顺序、发布验证版本、组织 e2e、向用户提交确认请求、确认后发布与核对、收尾关 issue | 不替开发会话写实现 |
| 开发会话 | 领一组 issue，写 plan、按选定路线在自己的 worktree 里实现并完成门禁，登记并维护自己那一行，在约定环境完成自己的 e2e | 不直接改主工作区，不发布，不关闭 issue |
| 用户 | 开版时给出想做的 issue，按分组开开发会话，在集成 agent 里当场确认发布 | — |

会话用有意义的名字标识职责，按各客户端的命名方式设置。

## 会话通信

- Claude Code 使用 `SendMessage`；等待空闲使用 `notify_when_idle`。
- 给 Codex 会话发送或回复消息，无论发送方是 Claude Code 还是 Codex，均使用 `codex queue --remote '<地址>' --thread '<UUID>' --message '<消息>'`；先取得接收方的会话 UUID 和 app-server 地址，消息注明发送者及回复地址。不得通过 `tmux send-keys` 或其他终端代输方式向 Codex 投递协作消息。
- 仅通知需协调的路径/版本依赖冲突、候选就绪、部署与验收结果及实质阻塞；证据写回登记行，不转发方案全文、例行进度或重复 ACK。收到需处理的消息后执行并回复实际结果；无需动作不要求 ACK，等待由对方消息驱动，不轮询。

## 开版

1. 用户对集成 agent 说要做哪些 issue。
2. 集成 agent 建批次 issue（标签 `release-train`，标题 `[发版批次] YYYYMMDD-N`），并按各 issue 预计改动的文件给出会话分组：会改同一文件的 issue 放进同一个会话，以减少之后的 rebase。
3. 用户按分组开开发会话，开场说明要做的 issue 和批次 issue 号。

### 仓库与批次归属

- 单仓改动在该仓库建批次 issue；跨仓改动由用户指定集成负责人和主批次所在仓库，其他仓库的 issue 引用主批次，不镜像登记状态。
- issue 一律记录完整 URL 或带仓库的标识，跨仓消息不得只用 `#N`。主批次登记每个仓库的源提交、依赖版本、合入与部署顺序、验收及回滚约束。
- 同一批次只有一个集成负责人；同一仓库主工作区同一时间只有一个集成负责人操作。已有集成占用时先协调顺序，不并发切分支或发布。
- 集中协调不合并服务、数据库、权限或发布生命周期。每个仓库独立检查、构建、部署和回滚；跨仓发布确认逐仓列出动作及依赖，不能把某一仓库发布成功当作整批验收通过。

### 入批截止

集成 agent 发出发布确认请求之前，新登记项都可以入批；截止时间由用户定，过了截止时间或确认请求一发出，这批就不再接收新登记项，后来的进下一批。已经发布的批次不再接收新登记项。晚入批者更新基线并重跑受影响的门禁；跨仓依赖或验收前提发生变化时，相关登记项也必须补验。不需要发布制品或部署服务的登记项（例如仅改文档）错过截止时间也可以在发布后再合入，不必等下一批。

## 登记

开发会话取得用户入批授权并写完 plan 后，在批次 issue 里登记一行；实施前完成登记。Builder-loop 取得 run id 后补回原行，一个 run 可覆盖多个 issue；原生执行注明执行路线，以开发会话和 worktree 标识实施单元。

- 覆盖的 issue（含仓库）、执行路线与 run id（原生执行填不适用）、会话名、worktree、plan 文件路径、改动路径；
- 状态：规划 / 开发 / 已合入 / e2e 通过（覆写，不追加历史）；
- 类型（可叠加）：仅文档或脚本、CLI 制品、需服务端重启、带 migration；
- 回滚约束（例如 migration 生效后回滚到哪个提交之前会改变数据语义）；
- e2e 清单：在本仓验证版本、测试环境或部署后的服务端上要验证什么，以及需要的跨仓依赖；
- 收尾：关闭 / 部分 / 不关。选「部分」必须写明剩余工作所在的 issue 号，没有就先立；选「不关」写原因。规划时填写，e2e 时可修正。

状态变化后改自己那一行，再按「会话通信」通知集成 agent：「批次 <完整 URL> 有更新」。

## 开发与合入

- 开发会话在独立 worktree 实施；原生执行也不直接修改集成主工作区。Builder-loop 的 worktree、门禁和 finalize 按其 Skill/runtime；原生执行在完成约定检查后交接提交与证据，由集成负责人合入。
- finalize 只生成本项交付提交，不代表已合入主干或上线。开发会话交接后，由集成 agent 在原登记行记录交付提交、接收后的主干提交和待发布批次；延期或阻塞要写明原因、负责人和后续批次或跟踪 issue，不让已完成项停在无人接收的分支。
- Builder-loop 会话同一时间只能有一个未复盘的 run；多个 issue 合进一份 plan，或依次执行。
- 向目标分支合入的提交都应属于某个批次；未入批的提交先通知集成负责人协调并取得用户入批授权，不把门铃消息视为授权。
- 合入顺序由集成负责人协调。目标分支已前进时，后合入者在隔离 worktree 更新基线并重跑受影响的门禁；旧基线证据不能替代集成后验证。Builder-loop 通过其 Skill/runtime 更新基线。
- 集成主工作区保持干净；构建前核对目标仓库、HEAD、工作树和构建来源，禁止发布夹带未登记改动的制品。

## 发版节奏

- **可单发**：只改 CLI 或文档、不需要服务端重启也不带 migration 的登记项，完成合入及门禁后，可由集成负责人按本仓发布约定单独交付。
- **攒批**：需要服务端重启或带 migration 的登记项，等同批次相关项完成合入后，按各服务依赖顺序部署；同一服务尽量一次完成切换。

## 发版

1. 发布验证版本或准备部署前，集成 agent 逐项核对已交付项是否进入主干、主干提交是否进入本批固定源，并在批次原登记行标明本批发布或明确顺延去向；逐仓核对发布工作区干净、远端主干包含源提交、依赖版本和全部提交差异。未登记提交单独列出并处理，不从批次登记推断整棵树的内容。
2. 按本仓约定发布验证版本并通知开发会话完成 e2e；没有验证环境的服务端先完成合入 HEAD 的检查，带 migration 时按本仓约定及用户授权演练，e2e 在部署后进行。各会话把结果和证据写回原登记行；本地测试、制品发布、部署健康和真实 e2e 分别记录。
3. 集成 agent 在自己的会话里给用户一份确认请求，逐仓列明版本与发布类型、源提交、登记项及未登记提交、平台验收缺口、依赖与部署顺序、服务重启与 migration、回滚边界及上线后 e2e。具体命令和准入门禁读取目标仓库入口；缺少可靠发布或恢复步骤时先补齐，不套用其他仓库命令。
4. 用户当场确认后只执行批准的固定源，不因主干前进夹带新项。完成后逐仓核对版本、进程和配置，并通知实际包含的每项开发会话：已部署源、部署时刻及证据入口；由各 owner 按其用户授权核实线上 e2e，结果写回原登记行。部署成功不等于 e2e 通过；按「收尾」一节处理覆盖的 issue，最后关闭批次 issue。

用户不在场时，流程最多推进到已授权的验证工作完成、确认请求已备好，然后停下等用户。自然事件待验、部分通过和未知分别标明，不写成 e2e 通过。

## 收尾

登记行到「e2e 通过」时，由集成 agent 按「收尾」列处理覆盖的 issue：「关闭」即关闭并补一条评论写明提交、批次和证据位置；「部分」先核对剩余工作的 issue 已存在，再在原 issue 写清本次覆盖的范围；「不关」只在原 issue 记下本次进展。开发会话不关闭 issue。

批次关门前逐行核对收尾动作都已执行，有任何一行未处理，批次 issue 不关闭。

e2e 需要等待自然事件或下一个时间窗口时，把验证方法写成评论挂到对应 issue 上，登记行状态写「e2e 转对应 issue URL 跟踪」，批次照常收尾。

任务收尾时核对分支与 worktree：仅在改动已进入主干或已确认的后继、无独有文件（含被忽略的资料）、无会话/任务/发布占用后回收临时 worktree 和废弃分支；有未提交内容、未决交付或占用不明时保留并在原 issue 说明。保留 run 账本、失败证据、发布快照和制品；不以清理代替功能收尾。
